# DBFlow UX 기능 후보 — 실제 제품·사용자 경험 리서치 기반

> 작성 2026-07-27. 세 갈래 리서치(① 실제 제품 기능 조사: Bytebase·Archery·Yearning·SQLE·Atlas·Redgate·DBmaestro,
> ② 승인 워크플로우 UX 패턴: GitHub/GitLab·Linear·ServiceNow·Brex·Slack/Notion,
> ③ 현재 DBFlow 웹 UI 공백 전수 탐색)를 종합한 **사용자 경험 중심** 후보 카탈로그.
> 거버넌스 중심 후보는 [roadmap-tier2-candidates.md](./roadmap-tier2-candidates.md) 참고 — 이 문서는 그와 중복되지 않는 항목만 담는다.
> 확정 스펙이 아니며, 구현 전 개발 사이클(brainstorm→스펙 검수→plan→plan 검수→구현→리뷰→머지)을 거친다.

**선정 필터**: 통제된 절차(사람 검수·결재·감사)를 **더 빠르고, 덜 잊히고, 더 정확하게** 만드는 UX만 채택.
절차를 건너뛰게 하는 편의 기능(무맥락 일괄 승인, 자동 승인 등)은 탈락.

규모 표기: **S**(1~2일) / **M**(3~5일) / **L**(1~2주+).

## 0. 기능 이전에 — 발견된 실버그 1건

UI 탐색 중 발견. 새 기능보다 먼저 고쳐야 한다.

- **CR 상세 페이지의 에러가 로드 후엔 보이지 않음** — `apps/web/app/(app)/change-requests/[id]/page.tsx:89`가
  `error && !cr`일 때만 에러 배너를 렌더링한다. CR이 이미 로드된 뒤 발생하는 모든 에러
  (승인 실패, 적용 실패, 롤백 실패, "반려 사유 필수" 클라이언트 검증)가 화면에 나타나지 않는다.
  빈 사유로 반려를 눌러도 아무 반응이 없는 상태. **규모 S, 최우선.**

## E. 검토·결재 루프 — "요청이 방치되지 않게"

승인 도구의 핵심 고통은 "아무도 안 봐서 요청이 묵는 것". 이 그룹이 그 문제를 정면으로 친다.

| # | 기능 | 설명 | 참고 | 규모 |
|---|------|------|------|------|
| E1 | **"내 결재 대기" 인박스 랜딩** | 대시보드를 "내가 결정해야 할 CR 목록(오래된 순)" + "내 요청(무엇에 막혀있는지)" 두 섹션으로. 현재는 숫자 카드만 있고 목록이 없음 | GitHub review queue, Linear inbox | S |
| E2 | **결재 대기 배지 (사이드바·탭 타이틀)** | 사이드바에 "나에게 온 결정"만 세는 숫자 배지, 그 외 활동은 점(dot). 브라우저 탭 타이틀에도 카운트 미러링. FYI까지 세는 순간 신뢰를 잃으므로 범위 엄수 | Slack 배지 철학 | S |
| E3 | **재검토 요청 버튼** | 반려 후 수정한 작성자가 "재검토 요청"을 누르면 해당 검토자 decision 리셋 + 재알림. 규제 조직 CR이 죽는 지점("이틀 전에 고쳤는데 검토자가 모름")을 직접 해소 | GitHub re-request review(공식 UI가 안 보여서 유명한 고통점) | S |
| E4 | **넛지 + 자동 묵힘 리마인더** | CR 페이지의 수동 "리마인드" 버튼(결재자당 1일 1회 제한) + SUBMITTED로 임계 시간 초과 시 자동 리마인더(DBFLOW_TZ 업무시간 존중). "확인했음" ack로 중단 가능 — ack 없이 넣으면 결재자가 채널을 뮤트해버림 | ReviewNudgeBot, Axolo | M* |
| E5 | **원클릭 결재 + 인라인 컨텍스트 프리뷰** | 인박스 행을 펼치면 대상 DB·환경·SQL 타입·구문 수·SQL 미리보기·리뷰 판정이 보이고 그 자리에서 승인/반려. 반려는 사유 필수, 승인은 프리뷰가 곧 "숙고의 증거" | Brex 2-click 승인, ServiceNow Approvals Hub | M |
| E6 | **적용 준비 체크리스트 위젯** | CR 상세 상단에 게이트 전수 표시: 결재 정족수·동결 기간·다음 작업창·백업 설정·SQL 리뷰 판정. 적용 버튼이 비활성이면 **이유를 인라인으로** — 말 없는 비활성 버튼 금지 | GitLab merge widget | M |
| E7 | **SQL 리뷰 결과를 status check처럼** | 린트 결과를 규칙별 이름 있는 체크 목록(통과/경고/차단)으로 접이식 렌더링. 검토자가 린터가 이미 증명한 것을 건너뛰고 의도 검토에 집중 | GitHub status checks | S~M |
| E8 | **위임 중 표시** | 결재자 칩에 "위임 중" 배지 + 인박스가 대결자에게 자동 라우팅됨을 표면화 (백엔드 위임은 PR #14로 완료, 노출만 부족) | ServiceNow OOO | S |
| E9 | **PROD 결재 확인 단계** | 롤백에는 `window.confirm`이 있으나 승인/반려에는 없다. 통제 절차 제품에서 오클릭 PROD 승인은 거버넌스 사건이므로, PROD 대상 CR의 결재에 확인 단계를 둔다 (Tier-2 A5 전자서명/재인증의 경량 선행형) | 21 CFR Part 11, ServiceNow | S |

*E4는 스케줄러+알림 발송 인프라(Tier-2 D1/A1 잔여)와 같은 슬라이스로 묶는 것이 자연스럽다.

## F. SQL 작성·검토 경험 — "에디터가 곧 제품"

중국계 SQL 工单 툴(SQLE·Archery) 사용기들이 수렴하는 불만이 전부 여기다: 자동완성 없음, 문법 오류 즉시 표시 없음, 결재 버튼이 스크롤 밑에 숨음.

| # | 기능 | 설명 | 참고 | 규모 |
|---|------|------|------|------|
| F1 | **리비전 diff + 승인 무효화** ⚠️정합성 | 반려 후 SQL 수정 시 리비전 간 side-by-side diff 제공, 기존 승인은 stale 처리. 없으면 결재자가 "지적된 한 줄만 고쳤는지, 절반을 몰래 다시 썼는지" 알 수 없음 — **승인 보증을 실제로 뚫는 유일한 구멍**. 현재는 아예 CR 수정 자체가 불가(반려되면 새로 타이핑)라 수정 기능+리비전 모델이 선행 | Atlas Activity&History, Tier-2 B4와 결합 | M |
| F2 | **SQL 에디터 승격 (CodeMirror/Monaco)** | plain textarea → 문법 하이라이팅 + 라인 넘버 + 제출 전 파스 오류 인라인 표시. 스키마 인지 자동완성은 2단계 | SQLE 사용기 불만 1순위, Archery 자동완성 | M |
| F3 | **SQL 표시 개선 (상세·diff·감사)** | `<pre>` → 하이라이팅 + 복사 버튼 + 다운로드 + 접기. CR 상세·스키마 diff·감사 메타데이터 공통 컴포넌트로 | Bytebase | S |
| F4 | **.sql 파일 업로드 + CR 복제 + 템플릿** | 드래그&드롭으로 파일 본문 투입, "이 CR 복제" 버튼, 조직 템플릿(승인된 변경 모양의 제도화 — 매월 반복되는 인덱스 추가·정기 퍼지 등) | Archery 工单, Bytebase 스크립트 업로드 | S~M |
| F5 | **스키마 브라우저 사이드바** | CR 작성 화면에서 선택한 대상 DB의 테이블/컬럼 트리 + 클릭 삽입 + 현재 DDL 열람. "안 보이는 테이블에 ALTER를 쓰는" 상황 제거 | Archery 表结构, Bytebase | M |
| F6 | **EXPLAIN 프리뷰 첨부** | CR 구문에 대해 대상 DB EXPLAIN을 실행해 검토 화면에 시각화. "이 UPDATE가 풀스캔인가"를 질문에서 표시된 사실로 | Bytebase ⌘+E | M |
| F7 | **라인 단위 코멘트 + 스레드 + 일괄 리뷰 제출** | SQL 라인에 앵커된 코멘트, resolve 가능한 스레드, GitHub식 "pending → 한 번에 제출(판정 포함)". 새 Comment 모델 필요 — Tier-2 D3의 구체화 | GitHub PR 리뷰 | L |
| F8 | **구문별 "확인함" 체크 + 변경 시 자동 해제** | 검토자별 파일 단위 viewed 상태 + 진행률, **SQL이 바뀌면 체크 자동 해제** — "내가 검토했다"를 특정 버전에 대한 주장으로 만듦(감사 방어력) | GitHub viewed checkbox | M |

## 채택하지 않거나 경계하는 것

- **일괄 승인(bulk approve)** — ServiceNow에 있지만 DBFlow 전제를 정면으로 깎는다. 저장 뷰(G2)가 가치의 대부분을 위험 없이 담당. 굳이 한다면 비프로덕션 한정 + 공통 사유 필수 + StatusHistory 개별 기록.
- **AI 리뷰 어시스트** — Yearning/Bytebase/Archery 모두 탑재했으나, 하려면 **advisory-only**(게이트·자동승인 절대 불가)로 엄격히 한정. 느슨하게 잡으면 안티비전으로 표류하는 1순위 항목.
- **다크모드·사이드바 접기·스켈레톤 로더** — 이미 구현되어 있음. 재제안 금지.

**1선 — "결재 인박스" 슬라이스 (E1+E2+E3+E8, 전부 S)** 🥇
기존 테이블 쿼리만으로 구성 가능. "일하러 들어와서 일을 찾는" 구조를 "로그인하면 일이 보이는" 구조로 뒤집는다.
E4(넛지)는 알림 발송 인프라(Tier-2 D1/A1 잔여)가 생기는 슬라이스에 얹는다.

**2선 — 리비전 diff + 승인 무효화 (F1)** 🥈
목록 전체에서 유일하게 **정합성 구멍**을 막는 항목. CR 수정 기능 자체가 없어서 반려=재타이핑인 현재 UX 고통도 함께 해소. Tier-2 B4(승인 산출물 무결성)와 한 몸.

**3선 — 에디터·목록 에르고노믹스 팩 (F2+F3+F4+G1+G2+G3+G4+G6)** 🥉
S~M 항목 묶음. 경쟁 툴 사용기들의 불만이 수렴하는 지점이라 "실제 제품 모방" 취지에 가장 부합. 도메인 개념 추가 없이 매일 쓰는 화면의 체감 품질을 올린다.

> 이후: E5·E6·E7(결재 화면 심화) → H1·H2(적용 UX) → F7·F8(라인 리뷰 스택) → H3·H4(대형 신기능).
